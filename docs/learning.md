# B7-1 학습 노트

## 1. 전체 흐름

브라우저 폼 → FastAPI route → 로그인 사용자 확인 → 입력 검증 → 최근 사용자 대화 조회 → AI API 서버 호출 → 응답/실패 정리 → DB 저장 → 화면 재렌더링 순서로 진행된다.

## 2. 인증과 접근 제어

브라우저에는 서명된 세션 쿠키가 있고 서버가 `user_id`를 읽어 DB 사용자와 연결한다. `/chat`, `/logs`, `/api/me/chats`는 로그인 사용자를 요구한다. AI key는 이 흐름에 포함되지 않고 서버 환경 변수에서만 읽는다.

## 3. 문맥 유지

전체 로그를 무제한 전송하지 않는다. `recent_context()`가 현재 사용자 ID로 필터링하고 최근 성공 대화 N개만 가져온다. 비용/길이 증가를 제한하면서 최소 문맥을 유지하는 전략이다.

## 4. 실패/타임아웃

`AIClient`는 timeout과 일반 upstream 오류를 다른 코드로 분류한다. 서비스는 예외 때문에 종료하지 않고 사용자에게 안전한 안내를 보여 주며 실패 대화도 DB에 남겨 운영 추적이 가능하다.

## 5. 설명할 수 있어야 하는 질문

1. 왜 AI API key를 브라우저가 아니라 서버 환경 변수에 두는가?
2. `request_id`가 서버 로그와 DB 추적을 어떻게 연결하는가?
3. `CONTEXT_TURNS`를 무제한으로 두면 어떤 문제가 생기는가?
4. 왜 다른 사용자의 대화를 context 조회 SQL에서 제외해야 하는가?
5. timeout을 설정하지 않은 외부 API 호출이 웹 서비스에 어떤 영향을 줄 수 있는가?
